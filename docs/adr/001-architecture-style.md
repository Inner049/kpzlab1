# ADR-001: Вибір архітектурного стилю

## Статус: Прийнято

## Контекст
Розробляється REST API застосунок Expense Tracker для управління особистими фінансами з функціями обліку витрат, категоризації та аналітичних звітів. Команда складається з 1 розробника, очікуване навантаження — до 1000 користувачів. MVP потрібно реалізувати за 4-6 тижнів, тому архітектура має бути простою, зрозумілою та не потребувати складної інфраструктури.

## Рішення
Використовувати **шарову архітектуру (Layered Architecture) з патерном MVC**, реалізовану через фреймворк FastAPI.

## Альтернативи, що розглядалися
- **Мікросервіси (Microservices):** відхилено, бо це надмірна складність для 1 розробника, проєкт не потребує незалежного масштабування компонентів і це суттєво сповільнить реліз MVP.
- **Моноліт без шарів (Big Ball of Mud):** відхилено, бо відсутність структури призводить до "спагетті-коду", який складно тестувати, підтримувати та розширювати.

## Наслідки
+ **Швидкість розробки:** зрозуміла структура дозволяє одразу почати писати бізнес-логіку.
+ **Простота тестування:** кожен шар можна тестувати ізольовано.
+ **Відповідність SOLID:** чітке розділення відповідальностей між маршрутами, сервісами та репозиторіями.
- **Обмеження масштабування:** при дуже великому навантаженні (100,000+ користувачів) монолітна база даних та монолітний бекенд можуть стати вузьким місцем.
